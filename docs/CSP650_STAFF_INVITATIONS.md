# Administrator-created staff and driver accounts

## How onboarding works

An administrator opens `/admin/staff`, enters a name, email, and Staff or Driver role, and selects **Create account and send invite**. FastAPI alone calls the Supabase Auth invitation endpoint using the server-only secret. Supabase creates the Auth user and sends its invitation email. FastAPI uses the returned Auth UUID to save an explicit role grant; the email and name are display snapshots, not authorization claims. The person opens the invitation link, sets a password at `/staff/accept-invite`, then signs in at `/staff/login`. The password is entered only into Supabase Auth from the invited person's browser; administrators never see or set it.

The existing UUID grant form remains available for a person who already has a confirmed SisaCare account, or to repair a grant if Supabase sent an invitation but the database write failed. In that partial-failure case the API returns the invited Auth UUID to the administrator. Do not invite an existing email to create a duplicate account; grant the existing UUID instead. Staff and Driver currently share the same collection permissions, but the grant keeps the selected title. Granting the other title revokes the previous collection title in the same database transaction.

## One-time setup

1. Apply the existing Phase 1 and Phase 2 Supabase migrations, then `supabase/migrations/20261109000100_staff_invitation.sql` using the project's established `supabase db push` workflow. Back up the database first. SQLite local development adds the new display columns automatically without deleting old grants.
2. Keep `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `backend/.env` or server secrets. The service-role key must never be placed in `frontend/.env.local`, frontend source, or a browser request. The backend also needs its existing publishable key for normal token validation.
3. Set `EMAIL_PUBLIC_BASE_URL` in `backend/.env` to the actual frontend origin, such as `http://localhost:5173` locally or the HTTPS site origin for the demo. FastAPI uses `${EMAIL_PUBLIC_BASE_URL}/staff/accept-invite` as the Supabase invitation redirect.
4. Add that **exact URL** to the **hosted** Supabase project under Authentication → URL Configuration → Redirect URLs. Local `supabase/config.toml` already allows the two localhost invite URLs. Set Authentication → Email Templates → **Invite user** subject to `Your SisaCare.AI collection team invitation` and paste the HTML from `supabase/templates/invite.html`. The version-controlled template is used by local Supabase; editing it does **not** update the hosted project's Dashboard template.
5. Configure Authentication → SMTP Settings in the **hosted** Supabase project with a real delivery provider, verified sender domain/address, and server-side credentials. Supabase Auth sends staff invitations, citizen signup confirmation, and password reset through this provider. The backend's `USER_SMTP_*` settings deliver citizen report-status messages; `ADMIN_SMTP_*` may point to Mailtrap for administrator notifications. Those backend settings do not configure Supabase Auth mail. Do not put SMTP passwords in frontend variables or committed files. Local Supabase CLI's `[local_smtp]` captures messages in its development inbox; it cannot prove Gmail delivery.
6. Sign in with an already trusted admin account. Only FastAPI's existing `require_admin_user` dependency can call `POST /api/collection/admin/staff/invite`. Staff access is checked against the active database grant on protected requests.

## API and recovery

`POST /api/collection/admin/staff/invite` accepts `{ "email": "worker@example.com", "display_name": "Worker Name", "role": "staff" }` and returns HTTP 201 with the new Auth UUID and `invitation_sent: true`. Invalid input returns 422; missing admin authority returns 401/403; an already existing Auth email returns 409. Supabase configuration/delivery failures return 503. A partial Auth/database failure returns 503 with the Auth UUID for the administrator to grant through the existing-account form. No passwords or Supabase secrets are returned.

`GET /api/collection/staff/invite/identity` accepts the invitation session as a Bearer token and returns the verified UUID and email only when that user has an active staff or driver grant. The password page calls it before displaying the form, ignoring any existing backend browser cookie. `GET /api/collection/admin/staff` now includes optional `email`, `display_name`, and `invited_at` for display. Older grants may have null values. `POST /api/collection/admin/staff/grants` still accepts a UUID and now fills name/email from the verified Supabase Auth user when available. The private role grant, not the display fields or client-supplied role, determines access. Revoke an account through the existing admin page and reassign active reports with a recorded reason.

The staff list also checks each active account against Supabase Auth and returns `verification_status` as `verified`, `unverified`, or `unknown`. The administrator page enables **Resend verification email** only for an active, unverified account with an email address. `POST /api/collection/admin/staff/{user_id}/resend-verification` repeats the Supabase invitation for an invited account; for a separately registered account it resends the signup confirmation. FastAPI checks the active grant and current Auth verification state again before sending, and rejects a second request within one minute of the last confirmation email. If Supabase is unavailable, the status is `unknown` and resend stays disabled. A verified person who still needs a password should use **Forgot password** on the staff sign-in page. Some Supabase Auth versions may refuse a repeat invitation; the endpoint reports that failure rather than claiming delivery. [Supabase documents new invitations for expired links](https://supabase.com/docs/guides/auth/users#inviting-users).

## Verification

Run `backend/.venv/Scripts/python.exe -m pytest tests/test_staff_invitation.py tests/test_csp650_phase2.py` from `backend`; run `npm test -- --run src/pages/AdminStaffPage.test.tsx src/pages/StaffAcceptInvitePage.test.tsx` and `npm run build` from `frontend`. These tests mock Supabase Auth and do not prove real email delivery.

In staging, invite a new Gmail address that is **not** a Supabase project team member. Confirm the message arrives in its Gmail inbox, inspect the sender and link, open the link in a fresh browser, enter mismatched passwords to verify the form blocks submission, then set matching passwords and sign in at `/staff/login`. Confirm the task dashboard appears. Independently check a citizen signup confirmation reaches a real Gmail inbox and an administrator status email reaches Mailtrap when that channel is configured. Also verify that a citizen receives 403 on the invite endpoint, an uninvited account cannot set a staff password through the invitation page, and a revoked grant blocks task access. If the email redirects to the site root, correct the hosted Supabase redirect allow list. An expired invitation must be reissued by an operator through Supabase Auth; the current in-app invite endpoint intentionally refuses to create a second account for an existing email. A successful Supabase invite API response or local email capture is **not** proof that Gmail received the message.
